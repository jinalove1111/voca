# Paul Easy Voca → 다학원 판매형 SaaS 전환 시 필요한 보안 요소 TOP 10

_작성: 2026-07-26. 순수 분석/전략 문서 — 코드/SQL/DB 변경 없음. 지금
당장 착수를 권장하는 게 아니라(현재는 학원 1곳, 111명 규모에서
안전하다), **"몇 학원까지 팔 것인가"라는 사업 결정이 실제로 나기 전에
경영진이 미리 알고 있어야 하는 것**을 정리했다(`PAUL_EASY_VOCA_MASTER_
PLAN.md` §0 "다학원 확장은 사업적 결정이 먼저 나야 착수" 원칙과 연결).
근거는 전부 기존 감사 문서(`docs/audit/2026-07-24-security.md`,
`docs/audit/2026-07-24-deployment-scale.md`) 및 이번 세션의 `v3_11`
코드 검토에서 실측/확인된 사실이다 — 새로 추측하지 않았다._

**현재 아키텍처의 근본 전제**: Supabase Auth를 쓰지 않고, "누구인지"는
전부 애플리케이션 레벨(학생 이름+PIN, 관리자는 **전역 단일** `ADMIN_PIN`)
로만 구분한다. 이 전제 자체가 "학원 1곳" 모델에서 나온 설계라 — 아래
10개 항목 상당수는 결국 "이 전제를 다학원용으로 어떻게 확장할 것인가"
하나의 문제로 수렴한다.

## TOP 10 (우선순위순 — 위쪽이 선행조건, 아래로 갈수록 그 위에 얹힘)

### 1. 학원 단위 데이터 격리 (`academy_id` 경계)

**현재 상태**: `classes` 테이블에 학원을 구분하는 컬럼이 아예 없다
(`docs/audit/2026-07-24-security.md` 실측 확인 — 현재 컬럼은
`id/name/class_type/created_at/spelling_test_enabled/spelling_hint_
enabled/wrong_answer_repeat_count/spelling_direction`뿐). 단일 Supabase
프로젝트로 여러 학원을 함께 서빙하는 구조로 통합하는 순간, 같은 anon
key로 모든 학원의 커리큘럼이 뒤섞여 조회/노출된다.
**필요한 것**: `classes.academy_id`(또는 `academies` 테이블 신설) +
모든 하위 쿼리(`units`/`words`/`students`/진행도 테이블)가 이 경계를
전제로 스코핑되도록 재설계. **이것이 없으면 아래 2~7번은 전부 의미가
없다** — 가장 먼저 결정해야 하는 단일 항목.

### 2. 학원별 관리자 인증 (전역 단일 `ADMIN_PIN` 폐지)

**현재 상태**: 관리자 인증이 환경변수 `ADMIN_PIN` 하나로 전체 시스템에
적용된다 — 학원이 2곳만 돼도 한쪽 학원 관리자가 다른 학원 데이터를
그대로 조작할 수 있는 구조(1번과 결합 시 파국적, `docs/audit/2026-07-
24-security.md` "왜 100명×20학원 규모에서 치명적인가" 절 참고).
**필요한 것**: 관리자 자격증명을 학원 단위로 DB에 저장(해시 처리,
`api/_pinAuth.js`의 기존 scrypt 패턴 재사용 가능)하고, 요청마다 "이
관리자가 이 학원 소속인가"까지 함께 검증. 학생 PIN이 이미 `students.
pin_hash`(테이블 기반)인 것과 동일한 모델로 관리자도 옮기는 것 —
새로운 개념이 아니라 기존 패턴의 확장.

### 3. 실질적 RLS(단순 "anon 전체허용/차단"이 아니라 학원 스코프 인식)

**현재 상태**: 이번에 검토한 `v3_11`을 포함해 이 저장소의 RLS는 전부
"anon 전체 허용" 아니면 "anon 전체 차단(서버만 씀)" 이분법이다 — 행
단위로 "이 요청자가 어느 학원 소속인지"를 판별할 방법이 구조적으로
없다(Supabase Auth 미사용의 직접적 귀결).
**필요한 것**: 2번(학원별 관리자 인증)이 발급하는 세션/토큰을 Supabase
RLS의 `auth.jwt()` 클레임(또는 최소한 서버 경유 요청의 헤더)에 실어,
정책이 `academy_id = 현재요청자.academy_id` 조건으로 행을 실제로
가른다. 지금의 "SELECT는 전체 허용" 패턴 자체가 다학원에서는 성립하지
않는다.

### 4. 학생 세션 검증 (studentId 호출자 바인딩)

**현재 상태**: `docs/audit/2026-07-24-security.md` [Low] 항목 — 세션
토큰 개념이 없어 `studentId`(UUID)만 알면 그 학생 명의로 입실시험
점수/XP를 대신 제출 가능. 지금은 "결제/PII 없음, 학원 내부 랭킹
한정"이라 Low로 유지 중이지만, **여러 학원의 학생 UUID가 한 시스템에
섞이는 순간 이 갭의 파급力(반경)이 학원 하나에서 전체로 커진다.**
**필요한 것**: 로그인 성공 시 짧은 서명 토큰 발급(HMAC 등, 기존 신규
의존성 없이 Node 내장으로 구현 가능 — PIN 해싱 때와 동일한 원칙) 후
쓰기 요청에 동봉·검증.

### 5. 관리자 PIN 강도/형식 강제 (다학원 최약점 리스크)

**현재 상태**: 학생 PIN은 `isWeakPin()`으로 약한 값을 서버가 거부하지만
관리자 PIN은 형식 검증 자체가 없다(`docs/audit/2026-07-24-security.md`
[High→Medium] 항목). 지금은 학원 1곳이라 리스크가 운영자 한 명의
선택에 달려있지만, **20학원이면 "가장 약한 고리 1곳이 나올 확률"이
실질적으로 올라간다**(같은 문서가 이미 이 논리를 명시).
**필요한 것**: 관리자 PIN도 학생 PIN과 동일한 서버측 강도 검증 —
2번(학원별 인증 DB화)과 자연스럽게 같은 작업으로 묶임.

### 6. 진짜 rate limit / brute-force 방어 (공유 상태 저장소)

**현재 상태**: 고정 1.5초 지연뿐 — Vercel 서버리스 특성상 병렬 요청에는
무력함이 이미 정량 확인됨(`docs/audit/2026-07-24-security.md`, 동일한
패턴이 `admin-content-write`/`grade-writing-answers` 두 Edge Function
모두에 반복됨 — 공격 표면이 이미 2곳). 지금까지는 CLAUDE.md 규칙 6(외부
의존성 최소화)과 충돌해 운영자가 의도적으로 보류해온 항목.
**필요한 것**: Upstash Redis/Vercel KV 등 공유 상태 저장소 기반 진짜
rate limit. **이것은 순수 기술 결정이 아니라 "유료 고객에게 파는
제품인가"로 무게추가 바뀌는 정책 결정** — 무료 학원 1곳 자체 운영과
유료 SaaS는 이 트레이드오프의 답이 달라진다.

### 7. 관리자 작업 감사 로그 (Audit Trail)

**현재 상태**: 누가 언제 어떤 반/단어를 만들고 지웠는지 기록하는
테이블이 없다 — `admin-content-write`가 매 액션을 처리하지만 로그를
남기지 않는다.
**필요한 것**: append-only 감사 로그 테이블(어느 학원의 어느 관리자
액션인지, `academy_id` 도입과 함께 설계하는 것이 자연스러움) — 유료
고객 간 "내 데이터가 왜 이렇게 바뀌었냐"는 분쟁의 최소 방어선이자,
5/6번(브루트포스)이 뚫렸을 때 사후 탐지 수단이기도 함.

### 8. 테넌트 오프보딩 / 데이터 삭제 절차

**현재 상태**: 이 저장소는 DROP 계열 구문을 훅으로 원천 차단하고
있고(`checkDestructiveSql.mjs`), 이는 안전을 위한 의도적 설계다. 하지만
유료 SaaS는 "계약 해지 시 데이터 삭제 요청"(계약/컴플라이언스 요구,
국내 개인정보보호법 관점에서도 학생 개인정보 삭제 요청권과 직결)에
응답할 절차가 필요하다.
**필요한 것**: 파괴적 SQL을 에이전트가 자유롭게 못 쓰게 막는 원칙은
유지하되(이건 계속 옳다), **운영자가 직접 통제된 방식으로 한 학원의
데이터만 정확히 제거할 수 있는 별도 절차/도구**(예: 학원 단위 논리
삭제 → 유예기간 → 운영자 수동 확인 후 물리 삭제)를 1번(academy_id) 위에
설계.

### 9. Vercel 유료 플랜 전환 + ToS 준수 (기술이 아니라 계약 리스크)

**현재 상태**: `docs/audit/2026-07-24-deployment-scale.md`가 WebSearch로
확정한 사실 — Vercel Hobby 플랜은 **비상업적 용도로 한정**되며 실제
계정 정지 선례가 있다. 지금은 학원 1곳(상업 계약 여부는 운영자 판단
영역)이라 당장의 위반 여부와 별개로, **여러 학원에 유료로 판매하는
순간 이 플랜 자체가 계약상 허용되지 않는다.**
**필요한 것**: 상업화 결정과 **동시에**(사후가 아니라) 유료 플랜 전환
— 이건 "보안 강화"라기보다 "서비스가 어느 날 갑자기 계정 정지로
전체 중단"되는 사업 연속성 리스크의 최소 방어선이라 이 목록에 포함.

### 10. 모니터링/알림 최소 체계 (이상 징후 탐지)

**현재 상태**: `docs/audit/2026-07-24-deployment-scale.md` — 모니터링/
알림이 사실상 전무. 지금 규모에서는 운영자가 직접 체감하는 이상(로그인
안 됨 등)으로 문제를 알아채지만, **20학원 규모에서는 한 학원의 이상
징후(예: 특정 계정에서 반/단어 쓰기 요청이 비정상적으로 급증 — 5/6번
브루트포스가 뚫렸다는 신호일 수 있음)를 사람이 수동으로 알아채기
불가능하다.**
**필요한 것**: 최소 비용(Vercel/Supabase 무료 내장 실패 알림은 지금도
즉시 활성화 가능)에서 시작해, 상업화 규모에 맞춰 점진적으로 — 7번
(감사 로그)이 쌓이는 이상 패턴을 알림으로 연결하는 것이 가장 이 앱의
기존 원칙(무료 우선, 최소 의존성)에 맞는 확장 경로.

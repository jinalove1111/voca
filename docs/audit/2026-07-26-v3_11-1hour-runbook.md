# v3.11 커리큘럼 락다운 — 1시간 실행 런북 (한국 복귀 후용)

_작성: 2026-07-26. `docs/audit/2026-07-26-v3_11-lockdown-execution-
review.md`(SQL 분석/변경전후/데이터영향/롤백)의 실행판 — 그 문서가 "왜/
무엇을"이라면 이 문서는 "언제/어떤 순서로/몇 분 안에"다. 겹치는 설명은
반복하지 않고 그 문서를 참조한다. **이 문서도 순수 문서 산출물이다 —
코드/SQL/DB/배포를 이 세션에서 전혀 변경하지 않았다.**

전제: 장거리 이동 직후 집중력이 평소보다 낮을 수 있는 상태에서, 혼자
운영자가 실행한다. 그래서 이 런북은 "판단"을 최소화하고 "확인 후 다음
칸"만 반복하도록 설계했다 — 애매하면 무조건 중단(진행 안 함)이 기본값.

## 1. 최종 실행 체크리스트 (시간 배분 포함, 총 60분)

| 시간 | 단계 | 무엇을 | 실패 시 |
|---|---|---|---|
| 0:00–0:05 | ① Secret 확인 | `supabase secrets list`로 `ADMIN_PIN`/`SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY` 3개 존재 확인 | 없으면 `supabase secrets set`으로 채우고 계속(SQL 실행 전이므로 롤백 불필요) |
| 0:05–0:15 | ② Edge Function 확인/배포 | `supabase functions list`에 `admin-content-write`가 `ACTIVE`인지 확인. 없으면 `supabase functions deploy admin-content-write` | 배포 에러 나면 **여기서 중단, SQL 실행 안 함** — 원인 조사가 오늘 목표가 아님 |
| 0:15–0:20 | ③ Vercel 확인 | Vercel 대시보드에서 최신 배포가 `main` HEAD(최소 커밋 `7234004` 이후) 기준인지 확인 | 구버전이 배포 중이면 재배포 트리거 후 배포 완료까지 대기(수 분 소요 감안, 아래 20분 이후 일정 밀림) |
| 0:20–0:25 | ④ 관리자 로그인 + 배선 라이브 확인 | 프로덕션 관리자 로그인 → 아무 반의 유닛 이름 하나 저장 시도 → 정상 저장 확인 | **실패하면 SQL 실행 절대 금지** — ①~③으로 돌아가 재확인. 이 단계는 SQL 실행 전 마지막 게이트 |
| 0:25–0:30 | ⑤ SQL 실행 | Supabase SQL Editor에서 `supabase_v3_11_lockdown_curriculum_write.sql` 실행 — **아래 "트랜잭션으로 감싸기" 권장사항 먼저 읽을 것** | 에러 메시지 그대로 기록, 6번(백업) 절차로 상태 확인 후 판단 |
| 0:30–0:45 | ⑥ 관리자 CRUD 테스트 | 아래 "4. 관리자 기능 테스트 목록" 전체 | 하나라도 실패 → **즉시 롤백**(6번 섹션) |
| 0:45–0:55 | ⑦ 학생 기능 테스트 | 아래 "5. 학생 기능 테스트 목록" 전체 | 실패 시 이 SQL과 무관할 가능성 높음(학생은 이 3테이블에 쓰기 자체가 없음) — 판단 기준은 6번 섹션 |
| 0:55–1:00 | ⑧ 기록 | `handoff.md` 최상단 세션 기록 + `PROJECT_BOARD.md` 카드 이동 + `.ai-status/` 갱신 | — |

**60분 룰**: 0:30 시점(SQL 실행 직전)까지 못 왔다면 오늘은 SQL을 실행하지
않는다. 사전 확인(①~④)에서 시간이 밀렸다는 것 자체가 뭔가 평소와 다르다는
신호이므로, 피로한 상태에서 마지막 단계(SQL 실행)를 서두르지 않는 것이
안전 원칙에 맞다 — 다음 기회에 ①부터 다시.

### SQL 실행 시 권장사항 — 트랜잭션으로 감싸기

원본 SQL은 9개 statement(3테이블 × 3줄)가 개별 실행되도록 작성돼 있다.
Supabase SQL Editor는 기본적으로 붙여넣은 전체 블록을 한 번에 실행하지만,
중간에 하나가 실패하면(예: 이미 같은 이름의 정책이 다른 정의로 존재하는
극단적 예외 케이스) 앞부분만 적용되고 뒷부분은 안 되는 "절반 적용" 상태가
될 수 있다. 아래처럼 **`begin;`/`commit;`으로 감싸서 실행하면** 9개 중
하나라도 실패 시 전체가 자동으로 원상복귀(atomic)되어 이런 애매한 중간
상태 자체를 원천 차단한다 — SQL 파일 자체를 수정하는 게 아니라 실행할 때
앞뒤로 두 줄만 추가하면 된다:

```sql
begin;

alter table classes enable row level security;
drop policy if exists "classes anon read only" on classes;
create policy "classes anon read only" on classes for select using (true);

alter table units enable row level security;
drop policy if exists "units anon read only" on units;
create policy "units anon read only" on units for select using (true);

alter table words enable row level security;
drop policy if exists "words anon read only" on words;
create policy "words anon read only" on words for select using (true);

commit;
```

## 2. 실행 전 백업해야 하는 것

`docs/audit/2026-07-26-v3_11-lockdown-execution-review.md` 3번 섹션에서
이미 확인했듯 이 SQL은 DML이 없어 **데이터 자체가 손상될 가능성은
구조적으로 없다.** 그럼에도 아래는 "혹시 몰라서"가 아니라 **1시간 제한 +
피로 누적 상태에서 실수 확률이 올라가는 것**에 대비한 최소 안전장치다 —
전부 5~10분 내 끝나는 가벼운 확인/기록이지 별도 백업 인프라 구축이
아니다.

| 백업 대상 | 방법 | 왜 필요한가 |
|---|---|---|
| **현재 정책 상태(비교 기준선)** | SQL Editor에서 `select schemaname, tablename, policyname, cmd from pg_policies where tablename in ('classes','units','words');` 실행 → 결과(현재는 빈 결과일 것) 캡처/기록 | 실행 후 같은 쿼리로 "의도한 정책만 정확히 생겼는지" 대조할 기준선 확보 |
| **`classes`/`units`/`words` 데이터 스냅샷** | Supabase 대시보드 Table Editor → 각 테이블 "Export as CSV" (또는 `select * from classes;` 등을 SQL Editor에서 실행 후 결과 복사) | 이 SQL 자체는 데이터를 안 건드리지만, 혹시 ⑥번 테스트 중 실수로 반/단어를 잘못 저장·삭제했을 때 되돌릴 참고 자료(이 SQL의 위험이 아니라 "사람이 테스트하다 실수할 위험"에 대한 대비) |
| **현재 프로덕션 배포 식별자** | Vercel 대시보드에서 현재 라이브 배포의 Deployment ID/커밋 해시 기록 | 뭔가 잘못됐을 때 "Redeploy" 버튼으로 즉시 이전 배포로 되돌릴 대상을 미리 알아둠(코드 롤백은 이 SQL 롤백과 별개 축) |
| **시크릿 값 자체** | 별도 백업 불필요 — `supabase secrets list`는 값을 보여주지 않는다(이름만). 이미 비밀번호 관리자 등에 보관돼 있다는 전제, 새로 적어두지 말 것(PIN을 평문으로 새 위치에 남기지 않는다 — 보안 원칙) | — |

**하지 않아도 되는 것**: 별도 pg_dump 전체 백업, Supabase 프로젝트 전체
스냅샷 — 이 SQL의 실제 위험 범위(3개 테이블의 정책 메타데이터)에 비해
과한 조치이고, Supabase 플랜에 따라 이미 자동 백업/PITR이 돌아가고 있을
가능성이 높다(운영자가 가입한 플랜에서 활성화돼 있는지만 대시보드에서
확인해두면 충분 — 이번에 새로 설정할 필요는 없음).

## 3. SQL 실행 후 반드시 확인할 화면

우선순위순 — 위쪽일수록 먼저, 문제 발견 시 그 자리에서 멈추고 6번(롤백
판단)으로 이동.

1. **관리자 로그인 화면** — PIN 입력 후 정상 진입하는지(이 SQL과 무관한
   경로지만 관리자 세션 자체가 살아있어야 이후 테스트 가능)
2. **관리자 → 반/유닛 관리 화면** — 목록이 정상 표시되는지(SELECT 영향
   없음 확인)
3. **관리자 → 반 설정 저장(유닛 이름 변경)** — 4번 게이트에서 이미
   확인했지만 SQL 실행 후 재확인
4. **관리자 → 단어 업로드(엑셀/PDF) 화면** — 화면 진입 + 실제 저장까지
   (아래 4번 목록에서 상세)
5. **관리자 → 쓰기 검토 큐(SpellingReviewQueuePanel)** — 목록 표시 +
   "이 답 인정" 버튼 동작
6. **학생 로그인 화면** — 정상 진입
7. **학생 → 단어 학습 화면(WordDetail)** — 단어/예문 정상 표시(SELECT
   경로, 영향 없어야 함)
8. **학부모 화면** — 조회 정상 동작(SELECT 경로만 씀, 영향 없어야 함)

## 4. 관리자 기능 테스트 목록

가능하면 테스트 전용 반/단어를 만들어 그 안에서 테스트하고 끝나면 정리할
것을 권장(2번의 "데이터 스냅샷"이 있으니 최악의 경우도 복구 가능).

| # | 기능 | 화면 | 대응 함수 | 예상 결과 |
|---|---|---|---|---|
| 1 | 반 생성 | 관리자 → 반 관리 → 새 반 추가 | `createClass` | 정상 생성, 목록에 즉시 표시 |
| 2 | 반 이름 변경 | 관리자 → 반 관리 → 이름 수정 | `renameClass` | 정상 저장 |

| 4 | 유닛 추가 | 관리자 → 반 상세 → 유닛 추가 | `addClassUnit` | 정상 생성 |

(예: ④번 롤백 후에도 같은 증상이면 이 SQL 문제가 아님).

## 6. 실패했을 때 Rollback 절차 (판단 트리)

세부 SQL은 `docs/audit/2026-07-26-v3_11-lockdown-execution-review.md`
4번 섹션 참고(방법 A: `disable row level security` 3줄, 멱등). 여기서는
"언제 롤백할지"의 판단만 다룬다.

```
④(관리자 배선 확인) 실패
  → SQL 아직 실행 안 함 → 롤백 불필요 → ①~③ 재점검, 오늘 중단 가능

⑤(SQL 실행) 자체가 에러
  → begin/commit으로 감쌌다면 자동 원상복귀(권장사항 따랐다면 걱정 불필요)
  → 감싸지 않았다면 위 "현재 정책 상태" 쿼리로 어디까지 적용됐는지 확인
     → 3테이블 다 안 됐으면: 원인 조사(오늘 중단 가능, 프로덕션 영향 없음)
     → 일부만 됐으면: 방법 A(전체 disable) 실행 후 재시도

⑥(관리자 CRUD 테스트) 하나라도 실패
  → 즉시 방법 A 롤백
  → 롤백 후 같은 테스트 재실행 → 정상화 확인
  → 원인은 대부분 "①~④ 중 하나가 실제로는 안 끝났음"(Edge Function
    미배포/Vercel 구버전/시크릿 누락) → 그 지점부터 재점검, 오늘 재시도
    안 해도 됨(취약점은 열려있지만 어제/오늘 상태와 동일 — 새로운 위험
    아님)

⑦(학생 테스트) 실패
  → 먼저 방법 A로 롤백 후 같은 증상이 계속되는지 확인
  → 롤백해도 증상 그대로면 이 SQL과 무관한 별도 문제 → 별도 이슈로
    분리, 원복 여부(⑤ 재실행 여부)는 그 별도 문제 해결 후 판단
  → 롤백하니 사라지면 이 SQL과 관련 → ⑥과 동일하게 원인 재점검
```

**공통 원칙**: 애매하면 롤백하고 다음 기회로 미룬다. 이 취약점은
2026-07-24부터 이미 열려 있던 것이라(신규 위험 아님) 하루이틀 더 열려
있어도 "상황이 악화"되는 게 아니다 — 반면 피로한 상태에서 롤백 없이
어중간하게 밀어붙이면 실제 서비스 장애로 이어질 수 있다. 서두르지 않는
것 자체가 이 런북의 핵심 안전장치.

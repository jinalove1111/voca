# ELLA Writing 수정 검증 — 회귀 테스트

- 작성일: 2026-07-27
- 대상 수정: `src/components/SpellingQuestion.jsx`(`markCorrect()` +
  `showManualNext` 안전망 버튼) — `docs/bugs/2026-07-26-ella-writing-spelling-stuck.md`
  8절 설계에 따라 구현됨(같은 세션, 코드 아직 커밋만 되고 push/배포 전).

## 방법론

- 로컬 dev 서버(`npx vite --port 5188`, 프로덕션과 동일한 실제 소스)를
  띄우고, 시스템 Chrome(`playwright-core`, 검증 목적 임시
  devDependency — `npm install --no-save`로 설치해 `package.json`/
  lockfile 변경 없이 사용 후 `npm install`로 완전히 제거함)로 실제 DOM을
  조작해 검증했다. `--dump-dom` 같은 정적 스냅샷이 아니라 실제 타이머/
  이벤트 순서를 그대로 관찰한다.
- 프로덕션 DB에 **QA\_ 접두어 임시 픽스처**(`QA_EllaWr` 반, `cat`/`dog`
  2단어, `QA_Ella1` 학생, 쓰기시험 활성화·`kr2en` 고정)를 만들어 사용하고,
  검증 종료 직후 전부 삭제했다(`removeStudent`/`deleteClass`, 기존 세션
  QA 픽스처 규칙 그대로).
- 로그인은 `/api/verify-student-pin`(서버리스, 로컬 `vite dev`에는 이
  라우트가 없음)을 거치지 않고, 실제 앱이 재방문 학생에게 쓰는 것과
  동일한 로그인 지속 메커니즘(`localStorage.paulEasyVoca_currentStudent`,
  `App.jsx` `SESSION_KEY`)을 그대로 주입해 "이미 로그인된 학생"을
  재현했다 — 판정/이동 로직 자체는 전혀 우회하지 않는다.
- 코드는 이번 검증 중 전혀 수정하지 않았다.

## 해석

가장 중요한 결과는 **시나리오 3**이다 — 원인 분석에서 40%로 지목한 실제
메커니즘(PC Chrome 확장 프로그램이 `play()`를 몽키패치해 동기 예외를
던지는 상황)을 그대로 재현했고, 수정 전 코드였다면 `setTimeout` 등록
자체가 실행되지 않아 학생이 정답 화면에 영구히 갇혔을 상황에서 수정 후
코드는 정상적으로 다음 문제로 넘어갔다. **시나리오 3b**는 그보다 더
근본적인 질문("오디오 문제가 아닌 완전히 다른 미지의 원인으로 자동
이동이 실패해도 학생이 절대 안 갇히는가")에 답한다 — 자동 타이머를
아예 죽여도 안전망 버튼이 나타나 학생을 구출한다.

## 한계 (정직하게 기록)

- 실제 Android/iOS 기기의 네이티브 Chrome은 사용하지 않았다(5번은
  뷰포트/UA/touch 에뮬레이션). 코드에 플랫폼 분기가 없다는 사전 분석과
  결합하면 신뢰도는 높지만, 100% 동일 보장은 아니다.
- 로컬 `vite dev` 환경에서 검증했다 — Vercel 프로덕션 서버리스 환경
  자체의 차이(콜드스타트, CDN 캐시 등)는 이 문서의 범위 밖이다. 실제
  배포 후 최소 1회 프로덕션 스모크 확인을 권장한다.
- 실제 오디오 하드웨어/스피커로 축하음이 "들리는지"까지는 확인하지
  않았다(헤드리스 브라우저) — `play()` 호출이 예외 없이 시도됐는지만
  확인했다(시나리오 2).
- 복합어(공백 포함 영어 단어) 채점 케이스는 이번 회귀 범위 밖(원 분석
  문서 TOP10의 원인 4번, 별도 이슈)이라 `cat`/`dog` 같은 단순 단어만
  사용했다.

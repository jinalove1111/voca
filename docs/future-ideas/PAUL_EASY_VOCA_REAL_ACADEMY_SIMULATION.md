# PAUL_EASY_VOCA_REAL_ACADEMY_SIMULATION.md — 50명 공부방 실운영 시뮬레이션

_작성: 2026-07-26. **순수 시뮬레이션/분석 문서 — 코드를 이 세션에서
전혀 수정하지 않았다.** 미래 SaaS 기능이 아니라 **지금 실제 코드가
실제로 어떻게 동작하는지**를 기준으로 시뮬레이션했다 — 근거는
`ARCHITECTURE.md`의 주요 플로우, `PROJECT_GUIDE.md`의 "헷갈리는 것
Top 5", `ROADMAP.md`/`handoff.md`의 실제 발견된 버그 이력, `PAUL_
EASY_VOCA_CURRENT_STATUS.md`의 P0~P2 목록이다. 추측이 아니라 **이미
한 번 실제로 발생했거나, 코드 구조상 발생 가능하다고 확인된 상황만**
다룬다._

**전제**: 원장 1인 운영, 학생 50명, 반 2~3개 규모(현재 실사용 학원과

## 1. 학생 가입 과정

### 정상 흐름
관리자가 `AdminScreen.jsx`에서 학생 이름+반 등록 → `api/admin-pin-
actions.js`(action: `bulk_generate_temp_pins`)로 임시 PIN 일괄 발급 →
원장이 **시스템 밖의 채널**(문자/카톡/구두)로 학생에게 임시 PIN 전달
→ 학생이 `StudentSelect.jsx`에서 이름 선택 + PIN 입력 → 최초 로그인
성공.

### 실제 발생 가능한 문제

| 상황 | 원인(코드 근거) | 심각도 |
|---|---:|---|
| 신규 학생 50명 일괄 등록 중 네트워크 불안정으로 일부 학생만 `pin_hash` 저장 실패 | `addStudent()` 성공 후 `/api/set-student-pin` 실패 시 계정이 DB엔 있지만 로그인도 PIN생성도 안 되는 상태로 고아화(`CURRENT_STATUS.md` P2 항목, 실제 QA 스윕에서 발견) | 중간 — 관리자가 로스터에서 "PIN 설정 허용"으로 수동 복구 가능하지만, 50명 일괄 작업 중이면 어떤 학생이 실패했는지 눈으로 확인해야 함 |
| 동명이인 학생이 등록됨(흔한 이름 — 예: "서준" 2명) | v1.6부터 `students.id`(UUID)로 안전하게 구분되지만, `StudentSelect.jsx`의 이름 선택 UI에서 학생 본인이 **어느 "서준"이 자기인지** 헷갈릴 수 있음(반 표시가 함께 있으면 완화되지만 완전 해결은 아님) | 낮음 — 데이터 유실 위험은 없음(과거 v1.6 이전 실사고와 다름), UX 마찰만 |
| 학생이 임시 PIN을 잊어버리고 부모가 대신 로그인 시도 | 5회 연속 실패 시 서버 측 잠금(`pin_locked_until`) | 낮음 — 잠금 자체는 안전장치지만, 잠금 해제는 관리자가 직접 해줘야 함(§7과 연결) |

## 2. 학부모 문의

### 실제로 들어올 법한 문의 3가지 (전부 시스템 동작에 근거)

1. **"어제 분명 공부했는데 캘린더에 기록이 없어요"** — 과거 실제
   버그였고(단어만 보고 카테고리를 못 채운 날 기록이 아예 안 생기던
   문제) 이미 수정됨(`ROADMAP.md`), 지금은 발생하지 않지만 **원장이
   이 이력을 모르면 처음 겪는 문의처럼 당황할 수 있음** — 응대 스크립트
   준비 가치 있음.
2. **"발음 점수가 왜 항상 만점이에요?"** — 이건 **버그가 아니라 설계**
   다: 녹음 성공(`blob.size>0`)을 곧 "발음 연습 완료"로 처리하고 실제
   발음 정확도는 채점하지 않는다(`ARCHITECTURE.md` 명시). **이 사실을
   학부모에게 어떻게 설명할지 미리 정리해두지 않으면 신뢰 문제로 번질
   수 있다** — §10 체크리스트에 포함.
3. **"다른 집 아이 진도가 저한테 보여요"/**반대로** "우리 아이 진도를
   다른 학부모가 볼 수 있나요?"** — `ParentScreen.jsx`는 **별도 인증
   없이 학생 이름만으로 조회**하는 기존 신뢰모델(설계 의도)이라, 다른
   아이 이름을 아는 학부모라면(같은 반 단톡방 등에서 흔함) 이론상 그
   아이의 진도도 조회 가능하다 — **50명 규모 공부방에서는 실제로
   발생 가능한 시나리오**(학원 1곳 폐쇄 커뮤니티라 지금까지 문제로
   드러난 적은 없지만, 외부 판매 시 §10에서 반드시 재검토 필요).

## 3. 선생님 업무 (원장 1인 = 교사)

### 일상 반복 업무 (실제 화면 기준)

- 반/단어 업로드(엑셀/PDF) — `ExcelUpload`/`PdfUpload`
- 학생 관리(반별 그룹핑, 반 이동, PIN 잠금 해제)
- 숙제 배정(오늘/미래 날짜)
- 대시보드로 반별 진도 확인
- **쓰기 검토 큐**(반복 오답 검토 — `SpellingReviewQueuePanel`) —
  아직 SQL/배포 미완료 상태(`CURRENT_STATUS.md`)라 지금은 수동 검토만
  존재
- (반별 설정 시) 입실시험 시작/종료, Word King/Season 수동 트리거

### 실제 마찰 지점

- `AdminScreen.jsx`가 여전히 큰 컴포넌트(하루새 57% 증가했다가 분리
  진행 중, `CURRENT_STATUS.md` F항목) — 화면 전환/스크롤이 원장
  체감상 느리게 느껴질 수 있음.
- 엑셀 업로드에 빈 파일/형식 오류 방어가 없음(`CURRENT_STATUS.md`
  P2) — 원장이 실수로 빈 시트를 올리면 의미 없는 에러만 뜨고 원인을
  스스로 파악하기 어려움.
- 반이 2~3개뿐이라도, 반별 설정(쓰기시험/게임화 on-off)을 매번
  탭을 오가며 확인해야 함 — Academy Owner Dashboard(`SAAS_
  ARCHITECTURE_PLAN.md` §9.2)가 아직 없어 "이 학원 전체 상태"를 한
  화면에서 보는 뷰가 없음.

## 4. 숙제 관리

### 실제 설계

`daily_assignments`(반의 오늘 배정 단어) + `student_daily_progress.
categories_completed>=4`(4개 카테고리 완료=숙제완료). **배정이 없으면
유닛 전체 단어로 자동 폴백** — 이게 실제로 원장이 자주 오해하는
지점이다.

### 실제 발생 가능한 오해 2가지

1. **"숙제를 안 냈는데 왜 학생 화면에 숙제가 떠 있죠?"** — 배정을
   안 하면 유닛 전체 단어가 그대로 숙제로 잡히는 것이 **정상 동작**
   (의도된 폴백)인데, 원장이 "배정 안 함 = 숙제 없음"으로 착각하면
   "시스템이 이상하다"고 느낄 수 있음.
2. **"미리 일주일치 숙제를 배정해뒀는데 학생이 다른 것만 하고 있어요"**
   — `FutureAssignmentPlanner`로 미래 배정을 해뒀어도, 그날이 되기
   전까지는 오늘 배정이 없으면 여전히 유닛 전체 폴백이 적용된다 —
   "예약이 걸려있다"는 상태가 화면에 충분히 안 보이면 원장이 혼란.

## 5. 시험 관리

### 입실시험(Entrance Test)

교사가 반/문항수/방향/시간 지정 후 시작 → 학생 홈에 배너 → 응시 →
서버 재채점(조작 방지 이미 적용됨) → 반별 랭킹/오늘의 VIP.

**실제 시나리오**: 학생이 등원 직후 바로 접속하지 않으면 배너를
놓치고 시간이 흘러버릴 수 있음 — 시험 시작을 학생에게 구두로 알려야
하는 오프라인 보완이 필요(시스템이 푸시 알림 등을 지원하지 않음,
`SAAS TOP10` 경쟁분석에서도 "재방문 트리거 부재"로 이미 지적된 갭).

### 쓰기시험(스펠링)

**실제 시나리오**: 학생이 최근 등록된 신규 단어에서 정답이지만 아직
`accepted_meanings`에 안 올라간 표현으로 답하면 즉시 오답 처리되고
`spelling_review_queue`로 들어간다 — **교사가 그 큐를 확인하기 전까지
학생 입장에서는 "억울한 오답"으로 기록이 남는다.** 이게 §3의 "쓰기
검토 큐를 매일 확인해야 하는" 실제 이유(§7과 연결).

## 7. 운영자가 매일 확인해야 하는 것

1. 오늘 반별 숙제 배정 여부(안 했다면 유닛 전체 폴백이 적용된다는 것
   인지, §4)
2. 어제 미완료 학생 확인 — 개입이 필요한지 판단(현재는 사람이 직접
   판단, `LEARNING_ANALYTICS_PLAN.md`의 위험학생 규칙은 아직 미구현)
3. **쓰기 검토 큐**(반복 오답) 확인·승인 — 방치하면 학생 입장에서
   억울한 오답이 계속 쌓임(§5)
4. PIN 잠금된 학생이 있는지 확인
5. (해당 주라면) 입실시험 결과/랭킹/VIP 확인
6. 전날 엑셀 업로드 등 데이터 변경이 정상 반영됐는지 최종 확인

**현실적 소요 시간**: 지금 기능 기준으로는 하루 10~15분 내외로
가능해 보이지만, **실측된 적은 없다** — §10 체크리스트에 이 항목을
실제로 검증할 것을 포함한다.

## 9. 반드시 사람이 해야 하는 부분

- **반복 오답 최종 승인/기각**(AI/통계는 판정 후보만 제시, 최종 확정은
  사람) — 이미 이 앱의 명시적 설계 원칙(자동 반영 없음)
- 신규 학생에게 임시 PIN을 실제로 전달(시스템 밖 채널)
- PIN 잠금 해제 여부 판단(진짜 본인이 맞는지 확인 — 전화/구두 등)
- 반/학생 삭제 등 파괴적 액션의 최종 확인
- **발음 실제 정확도 피드백** — 시스템이 채점하지 않으므로, 진짜
  발음 교정은 지금도 앞으로도 사람(교사)이 직접 들어야 하는 영역
  (`AI_LEARNING_ENGINE_PLAN.md` §10.3이 이미 이걸 "선행 과제"로 지목)
- 입실시험 시작 타이밍 결정(반 상황에 맞는 교사 판단)
- 업로드한 엑셀 콘텐츠 자체의 정확성(오탈자·오역) 검수 — 시스템은
  형식만 확인, 내용 정확성은 사람 몫

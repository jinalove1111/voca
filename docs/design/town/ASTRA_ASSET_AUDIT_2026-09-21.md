# Paul Town V2 — Astra 비주얼 에셋 전수 감사 (2026-09-21)

이 문서는 `docs/design/town/ASTRA_HANDOFF_2026-09-21.md`(이하 "핸드오프
문서")가 명시적으로 미룬 작업 — **실제 이미지 파일 154개를 하나하나 열어
판단하는 전수 비주얼 감사** — 를 수행한 결과다. 이 세션은 문서 작성만
했고 이미지 파일/제품 코드/테스트 코드를 전혀 이동·수정·삭제·신규 생성하지
않았다(§ 마지막 "검증한 것" 절 참고).

**중요한 정정**: 팀장이 사전에 제공한 스코프 센서스(`src/assets/town/*`
140개 + `src/assets/paul/*` 22개 = "총 약 162개")는 `.gitkeep` 플레이스홀더
파일과 `index.js`/`assetManifest.js` 같은 순수 데이터 파일을 이미지로
잘못 카운트한 결과다. 실제로 열어서 판단할 수 있는 실제 이미지 파일
(`.png`/`.webp`)은 **정확히 154개**다(town 133개 + paul 21개). 아래 §2가
정확한 산출 내역이다. 이 문서의 모든 개수·표는 이 154개 기준이다.

## 1. 감사 범위와 판정 기준

- **범위**: `src/assets/town/**/*.{png,webp}`, `src/assets/paul/**/*.png`
  전수(154개) + Town V2 컴포넌트(`src/components/town/v2/*.jsx`)에 내장된
  이모지/그라디언트/그림자 등 코드 기반 시각 요소.
- **제외**: `.gitkeep`(빈 디렉터리 유지용 Git 관례 파일, 이미지 아님),
  `assetManifest.js`/`index.js`/`env/index.js`(순수 데이터/배선 파일,
  이미지 아님). `public/`은 검색 결과 Town 관련 파일이 0개임을 직접
  확인했다(`find public -iname "*town*"` 결과 없음).
- **판정 기준**: 이 세션이 Read 도구로 실제 픽셀을 렌더해 육안 확인한
  카메라 각도/원근, 투명 배경 여부, 접지 그림자 유무, 아트 스타일
  일관성, 지도 아이콘 스케일에서의 적합성. 치수/파일 크기는 추측이 아니라
  PNG IHDR 청크 / WebP(VP8/VP8L/VP8X) 헤더를 직접 파싱하는 Node 스크립트로
  실측했다(외부 라이브러리 0개, CLAUDE.md 규칙 6과 동일 정신).
- **근접 동일 자산 그룹화 공시**: env/ 디렉터리의 path/fence/hedge/shrub/
  flower/river 계열처럼 같은 패밀리로 보이는 항목은, 각 패밀리에서 최소
  1~2개를 실제로 열어 카메라 각도·스타일·투명도가 같은 패밀리임을 확인한
  뒤 표 1행으로 묶었다 — 존재/분류(경로·사용여부·카테고리·포맷·용량)는
  154개 전부 개별적으로 프로그램으로 확인했고, 그룹화는 "심층 시각 판단"
  칸에만 적용했다(아래 §3/§4 표에 그룹 여부를 명시).

번도 배치되지 않은" 유일한 항목**이다. 나머지 34개 env 키는 모두 1회 이상
`ENV_PLACEMENTS`에서 실사용을 확인했다.

## 4. 표 — 미사용 에셋(파일은 존재하나 어떤 코드도 import하지 않음)

69개 전부 **23개 카탈로그 항목의 `@2x.webp`/`.png`/`@2x.png` 3변형**이다
(23×3=69, 남김없이 일치). "실수로 방치된 죽은 파일"이 아니라 **의도된
계약**임을 코드로 확인했다 — `scripts/validateTownAssetCandidate.mjs`
(외부 의존성 0개 자체 제작 검증 도구, `--audit` 모드를 이 세션이 실제
실행해 확인)가 신규 자산 드롭인마다 "4파일 세트(.png/.webp/@2x.png/
@2x.webp) 전부 존재"를 요구한다 — 향후 반응형 `srcset`/레티나 지원을
염두에 둔 선제적 산출물이지, 현재 어떤 `<img>`/CSS도 `@2x`나 `.png`
변형을 실제로 요청하지 않는다(이 세션이 `@2x` 문자열로 `src/**/*.{js,jsx}`
전체를 grep해 실사용 0건 확인, 매칭된 14개 파일은 전부 `docs/design/
town/*.md`/`*.html` 목업/`handoff.md`/`.ai-status/*.json`의 프로즈 언급뿐).

| 그룹 | assetKey당 파일 | 총 개수 | 총 용량 | 상태 |
|---|---|---|---|---|
| `@2x.webp`(레티나 webp) | 1개 | 23 | 957,775 bytes(935.7 KB) | 준비됨, 미배선 |
| `.png`(비 webp 원본/폴백) | 1개 | 23 | 560,833 bytes(547.7 KB) | 준비됨, 미배선 |
| `@2x.png`(레티나 png) | 1개 | 23 | 941,789 bytes(919.7 KB) | 준비됨, 미배선 |
| **합계** | | **69** | **2,460,397 bytes(약 2.40 MB)** | |

env/의 35개는 §3-2에서 이미 "사용 중"으로 분류했다(전부 `env/index.js`가
import). ui/는 실제 파일이 0개라 이 표에 해당 없음. backgrounds/ 6개는
전부 `TownGrid.jsx`가 사용 중(§3-3). **따라서 미사용 파일은 정확히
69개뿐이며, 전부 같은 원인(레티나/포맷 변형 미배선)이다** — "테스트
전용"이나 "문서 전용" 파일은 이미지 파일 중에는 없었다(문서/HTML
목업은 이미지를 직접 담지 않고 경로만 텍스트로 언급한다).

   전용 프레이밍).
2. **캐릭터로 전용 가능한 다른 자산 존재 여부** — `src/assets/` 전체를

### 5.6 큰 Paul 초상화를 그대로 축소하면 구체적으로 무엇이 깨지는가

- **프레이밍 불일치**: 얼굴+상반신만 있는 그림을 14~30px로 축소하면
  town의 다른 스프라이트(집 전체, 벤치 전체, 동물 전신)와 달리 "잘린
  얼굴 하나"만 보인다 — 다른 모든 오브젝트가 전신/완전한 형태로 보이는
  화면에서 혼자만 이질적이다.
- **원근 불일치**: 초상화는 카메라를 정면으로 바라보는 인물 사진 구도
  (스튜디오 촬영/셀카 구도)인 반면, town의 오브젝트(건물/나무/동물)는
  §3-1에서 확인했듯 3/4 정면 스토리북 일러스트 구도다 — 걷는 방향에 따라
  좌우 반전이 필요한 캐릭터가 정면 고정 초상화이면 "제자리에서 회전하는
  스티커"처럼 보인다.
- **의상 고정**: 21장 모두 같은 검은 셔츠+모자가 고정 의상이라(§3-4) 어떤
  reaction을 골라도 "걷기/앉기"에 맞는 자세 변형이 전혀 없다(팔다리 자체가
  프레임 밖).
- **투명 여백 불균형**: 초상화는 얼굴 중심으로 크롭돼 있어 세로로 긴
  "서 있는 전신" 실루엣이 필요한 지도 캐릭터 앵커(`anchor:
  'bottom-center'`, `assetManifest.js:47`과 동일 관례)와 맞지 않는다 —
  발이 어디인지 정의된 여백이 없다.
- **결론**: 새 스프라이트 제작이 필요하다는 것은 제안이 아니라 사실
  확인이다 — §5.1~5.5가 "존재하지 않음"을 코드/파일시스템으로 직접
  검증했고, §5.6이 "있는 걸 억지로 쓰면 안 되는 구체적 이유"를 제시한다.

## 7. 원근/아트 스타일 불일치 사례(코드/이미지로 직접 확인)

1. **town/index.js 카탈로그(23개) vs env/index.js(35개) 간 카메라 각도
   불일치** — §3-1의 건물/장식/자연/동물은 일관되게 "3/4 정면"(지면에서
   약간 위 각도로 내려다보되 정면성이 강한 스토리북 구도)인 반면, §3-2가
   확인했듯 env의 grass/path/river 계열(17개)은 **거의 수직에 가까운
   top-down**이다 — 같은 씬에서 건물은 옆에서 보고 바닥은 위에서 보는
   구도가 공존한다. 지금은 오브젝트가 배경 위에 낱장으로 얹히는 방식이라
   두드러지지 않지만, 걷는 캐릭터가 도입되면 "캐릭터가 위에서 본 길
   위를 옆에서 본 건물 사이로 걷는" 두 원근이 한 화면에서 동시에
   지각되기 쉬워진다.
2. **env 내부에서도 두 계열 공존** — 같은 env 레지스트리 안에서도
   fence/hedge/shrub/flower 계열(18개)은 §3-2가 확인했듯 **정면
   elevation**이라 grass/path/river(17개)의 top-down과 또 다르다 —
   "환경 = 한 원근"이 아니라 env 자체가 이미 두 원근의 혼합이다.
3. **paul 초상화(21개) vs 지도 오브젝트 전체** — §5.6에서 이미 상세
   서술 — 정면 인물 사진 구도 vs 3/4 스토리북 구도, 지도 캐릭터로 쓰기엔
   원근 자체가 다른 촬영/작화 방식이다.
4. **backgrounds/(V1, 6개) vs env/(V2, 35개)** — §3-3에서 확인했듯 톤은
   유사하지만 서로 다른 원화이며 완전히 분리된 파일 세트다 — 2.5D
   프로토타입이 어느 쪽을 베이스로 삼을지(또는 제3의 새 배경을 만들지)는
   아직 결정되지 않은 시각적 의사결정 사항이다(§14에 등록).

## 11. 권장 모바일 해상도

기존 계약을 그대로 따르는 것을 권장한다(새 기준 발명 안 함):
- `assetManifest.js`가 이미 모든 P0 항목에 대해 base(1x)/canvas2x(2x)
  2단계만 정의한다(§3-1) — 3x/4x 없음. 2.5D 캐릭터도 이 2단계 관례를
  그대로 따를 것을 권장.
- base 해상도는 실제 렌더 폭(§5.3 계산: sm 기준 씬 폭의 3.575~7.8%)의
  약 2배 픽셀 밀도로 이미 맞춰져 있다(예: bench base 72px vs 390px
  뷰포트에서 실제 렌더 약 14~30px — 표준 레티나 여유). 캐릭터도 동일
  비율(base=실제 최대 렌더 픽셀의 약 2~2.5배)을 권장.
- @2x는 §4가 확인했듯 **현재 어떤 P0 항목도 실제로 `srcset`/미디어쿼리로
  요청하지 않는다** — 2.5D 프로토타입이 @2x를 실제로 활용하려면 캐릭터
  자산 도입과 함께 `<img srcset>` 또는 `image-set()` CSS를 새로 배선해야
  한다(기존 파일이 있다고 자동으로 쓰이지 않는다는 점을 명확히 인지할
  것 — §4의 69개가 이미 이 함정의 실사례).

## 14. 구현 전에 사람이 결정해야 할 시각적 사항

1. **캐릭터 아트 스타일 방향** — town 오브젝트의 "3/4 정면 스토리북"

   이 문서가 대신 정하지 않는다.
2. **캐릭터가 "Paul"인지 "학생 아바타"인지** — 핸드오프 문서도, 이
   문서도 이 정체성을 확정하지 않았다 — paul/의 고정 의상(검은 셔츠+
   모자)을 캐릭터에도 반영할지는 브랜드 의사결정.
3. **§7-1/§7-2가 확인한 원근 불일치(3/4 정면 오브젝트 vs top-down
   env 타일)를 어느 방향으로 통일할지** — 오브젝트 쪽에 캐릭터를
   맞출지(이 문서 §8의 기본 제안), env 타일 쪽을 나중에 3/4로
   다시 그릴지는 상당한 재작업 범위 차이가 나는 결정이라 사람 승인
   필요.
4. **§4의 69개 미배선 변형을 그대로 둘지(향후 @2x 배선 예정), 정리할지**
   — 이 문서는 삭제를 제안하지 않는다(팀장 지시로 이미지 파일 이동/삭제
   금지 범위), 다만 다음 세션이 "왜 파일이 안 쓰이는지" 궁금해하지 않게
   이 문서로 원인을 기록해 둔다.
5. **backgrounds/(V1) vs env/(V2) 중 2.5D 프로토타입의 베이스로 어느
   쪽 톤을 계승할지**(§7-4) — 둘 다 "정답"이라 코드/파일 근거만으로는
   결정할 수 없다.

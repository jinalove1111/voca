# PAUL PHONICS 학습 발달 기록 설계 (257차, 2026-10-11)

상태: **설계 + 샘플 미리보기만**. 저장 기능, 테이블, 서버 경로는 만들지 않았다. 화면(학생 `ppg-*`, 관리자 `ppa-*`)은 가상의 `샘플반` 데이터만 보여 주고 상단에 "샘플 데이터 — 실제 학생 기록이 아닙니다"를 항상 표시한다.

## 1. 목표

1. 아이가 Book별 진도, Unit 시험 결과, 반복해서 틀린 소리, 복습할 단어, 최근 활동을 본다(다른 아이와 비교·순위 없음).
2. 선생님이 반 전체의 진도·시험·취약 소리를 한 화면에서 보고, 학부모 상담용 요약 문장을 얻는다.
3. 추측하지 않는다: 모든 문장은 횟수·점수에서 규칙으로 만든다(AI 호출 없음, 규칙 7).

## 2. 기록 모양 (record shape)

- 시도(attempt): 기존 `phonicsAttempt()` 결과 + `at`(ms). 필드: `studentId, gameId, bookId, unitId, step, targetPhonemes, itemId, correct, retries, completed, at`.
- Unit 시험: `{ studentId, bookId, unitId, unitTest: { score, total }, at }`.
- 모든 계산은 `src/utils/phonics/progress.js`의 순수 함수(입력 순서와 무관, 입력을 바꾸지 않음): `bookProgress`, `unitTestResults`, `weakPhonemes`, `reviewWords`, `recentActivity`, `improvement`, `recommendations`, `parentSummary`, `classOverview`, `classWeakPhonemes`.
- 완료 규칙: Unit 시험을 봤거나, 끝낸 항목 6개(Book 1은 시험이 잠겨 있어 소리 풍선 3개) 이상이면 "완료".
- 취약 소리: 시도 3번 이상, 틀림 2번 이상, 오답률 40% 이상.
- 복습 단어: 같은 단어를 2번 이상 틀렸거나 가장 최근 시도에서 틀린 단어.

## 3. 개인정보와 식별

- 학생 식별은 `students.id`(UUID)만(규칙 4). 이름은 표시용이고 키가 아니다. 샘플 id는 `sample-0001`처럼 UUID가 아니라서 실제 학생과 섞일 수 없다.
- 음성·녹음은 저장하지 않는다. 정답 여부, 재시도 횟수, 시각만 저장한다.
- PIN 관련 컬럼은 건드리지 않는다(규칙 11).
- 학부모·다른 학생에게는 노출하지 않는다. 학생은 자기 기록만, 관리자는 반 전체.

## 4. 쓰기 경로 선택지 (서버리스 함수 12개 한도)

현재 `api/`에 함수 13개 파일 중 `_pinAuth.js`는 공용 모듈이라 함수는 12개이고, Vercel 한도(12)에 닿아 있어 **새 함수 파일을 추가할 수 없다**.

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 기존 엔드포인트에 새 `action` 추가 (예: `submit-entrance-result.js`처럼 이미 서버에서 UUID로 검증하는 곳) | 함수 수 그대로, service_role 키가 서버에만 있음, 학생 세션 검증 재사용 | 한 파일이 하는 일이 늘어남, 해당 파일 소유자와 조율 필요, 배포 단위가 같아 롤백이 거칠다 |
| B. service_role 전용 RPC(Postgres 함수) + 기존 엔드포인트가 호출 | 검증·중복 제거를 SQL 한 곳에서 원자적으로 처리 | 어차피 호출하는 서버 경로가 필요(A와 결합), 마이그레이션이 더 커짐 |
| C. 브라우저 anon 키로 직접 insert | 서버 코드 없음 | RLS 정책이 필요해 학생 사칭 위험(anon이 임의 student_id로 쓸 수 있음), 규칙 4·11 정신에 반함 — **채택 안 함** |

**권고: A** — 기존 학생 인증을 이미 하는 엔드포인트에 `action: 'phonics-progress'`를 추가한다. 한 번에 여러 시도를 배치로 받고(`client_key`로 중복 제거), 서버가 `students.id`를 세션에서 확정한다. 구현하지 않는다.

## 5. 오프라인·중복

- 시도마다 `client_key`(예: `세션id:순번`)를 만들어 둔다. 서버는 `(student_id, client_key)` 유일 인덱스로 중복 재전송을 무시한다(초안 SQL에 포함).
- 오프라인이면 메모리 큐에 쌓다가 온라인이 되면 배치 전송, 실패하면 재시도(최대 횟수 제한), 영구 저장소 사용은 별도 승인 사항.

## 6. 운영자 승인이 필요한 것

1. `supabase_v3_51_phonics_progress_DRAFT.sql` 검토·승인·수동 실행(규칙 8). 지금은 아무도 실행하지 않았고 코드가 참조하지 않는다.
2. 쓰기 경로(A 권고)와 대상 엔드포인트.
3. 기록 보관 기간, 학부모 공개 범위.
4. 단어·소리·그림·녹음 자체의 승인(여전히 전부 임시 — 기록 기능과 별개).

## 7. 도입 순서 (플래그 뒤)

1. (지금) 샘플 화면 + 순수 함수 + 초안 SQL — 학생 데이터에 영향 없음.
2. SQL 승인·실행 → 테이블만 존재(앱은 모름).
3. 서버 `action` 구현 + 테스트(플래그 OFF).
4. 클라이언트 기록 큐(플래그 OFF) → 테스터 학생만 ON.
5. 샘플 화면을 실제 기록으로 교체(샘플 배너 제거), 테스터 → 일부 반 → 전체.
6. 각 단계에서 `phonics_*` 테이블 부재를 감지해 기록을 건너뛰고 기존 동작을 유지한다(규칙 9).

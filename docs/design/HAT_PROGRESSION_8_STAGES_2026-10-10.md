# 8단계 모자 승급 설계 (제안) - 2026-10-10

상태: **제안(설계 전용)**. 이 문서는 어떤 임계값·코드·SQL도 바꾸지 않는다.
아래 모든 숫자·규칙은 운영자 승인 전까지 제안이다. src/SQL/git 변경 없음.

운영자 요청: 기존 업적 수집 모자와 **별개로**, 순차 8단계 승급 모자를 둔다.
색 순서: 밝은 핑크 -> 빨강 -> 주황 -> 초록 -> 파랑 -> 남색 -> 보라 -> 금색.

## 0. 한 줄 결론 (제안)

- 기준 지표는 **XP 원장 누적**(기존 5랭크 곡선 0/50/150/400/800을 그대로 경계로 포함).
- 8단계 경계: **0 / 25 / 50 / 100 / 150 / 250 / 400 / 800 XP**.
- 상위 단계(4~8)에만 "서로 다른 단어 수" 하한을 겹쳐 같은 문제 반복 부풀리기를 막는다.
- 승급 모자는 **기본 모자 + 진행 표시**, 수집 모자는 **장착 선택 우선**. 인벤토리에 쓰지 않는다.
- DB/SQL 없음. 이미 동기화되는 XP 원장 + 학습 기록에서 순수 파생. 신규 플래그 기본 OFF.

### 2.2 제안 임계값 (제안, 미적용)

기존 5랭크 경계 50/150/400/800을 그대로 보존하고, 사이에 25/100/250을 추가한 8개 경계다. 기존 랭크 표시와 단계가 어긋나지 않는다.

| 단계 | 색 (이미지 키) | 최소 XP | 최대 활동 시 소요(18XP/일) | 가정 활동 시 소요(10XP/일) | 서로 다른 단어 하한(보조) |
|---|---|---|---|---|---|
| 1 | 밝은 핑크 (pink) | 0 | 시작 | 시작 | 0 |
| 2 | 빨강 (red) | 25 | 2일 | 3일 | 0 |
| 3 | 주황 (orange) | 50 | 3일 | 5일 | 0 |
| 4 | 초록 (green) | 100 | 6일 | 10일 | 10 |
| 5 | 파랑 (blue) | 150 | 9일 | 15일 | 20 |
| 6 | 남색 (navy) | 250 | 14일 | 25일 | 40 |
| 7 | 보라 (purple) | 400 | 23일 | 40일 | 80 |
| 8 | 금색 (gold) | 800 | 45일 | 80일 | 150 |

- 10XP/일은 **미측정 가정**이다. 운영자가 `xp_totals` 분포(읽기 전용 SELECT)로 확인한 뒤 경계를 조정한다. 경계는 배열 한 곳에서만 정의한다 (`RANKS`와 같은 방식, `paulRankShared.js:57-61`).
- 400 -> 800 구간이 길다(최대 22일). 기존 왕관 800을 보존한 대가다. 대안은 부드러운 기하 곡선 0/30/70/130/220/350/550/800이다. 이 경우 기존 랭크 경계(50/150/400)와 단계 경계가 어긋난다. 운영자 질문 Q2.
- 단어 하한은 "최종 단계 = min(XP 기준 단계, 단어 기준 단계)"로 적용한다. 하한 수치는 `gardenPoints` 분포(중앙값 20, 최대 279)에 맞춘 **잠정값**이며 실측 후 조정한다. 하한 8단계 150은 현재 대다수 학생에게 높다. 이것은 의도다(진짜 단어왕 수준, 수집 모자 `hat_crown`의 200 클리어와 같은 급).

## 3. 현재 단계와 다음 단계까지 진행 표시

| 위치 | 제안 | 재사용 |
|---|---|---|
| Dashboard 랭크 줄 (`Dashboard.jsx:744-750`) | 문구에 "승급 n/8 · 다음까지 XP m" + 가는 진행 막대 추가. 기존 랭크 문구는 유지 | `rankState` 훅 결과 (`usePaulRank.js:28`) |
| StudentHome 헤더 (`StudentHome.jsx:62`) | 장착 모자가 없을 때만 승급 모자 그림 표시(현재는 👑 폴백, `handoff.md:78`) | `hatImageFor` 계열 |
| HatCollection 상단 | 8칸 띠: 도달한 단계는 색, 미도달은 실루엣, 현재 단계 강조 | `HAT_IMAGE_BY_COLOR` |
| 성장(Growth) 화면 | 같은 띠 컴포넌트 재사용 (위치 확정은 구현 시) | 위와 동일 |

- 진행률은 `computeRankState`의 `progressRatio` 아이디어를 그대로 쓴다: `(xp - 현재경계) / (다음경계 - 현재경계)`, 최고 단계는 1 (`paulRankShared.js:215-217`).
- 신규 저장소 없음. 입력은 이미 `usePaulRank`가 읽는 `xp`(Dashboard에서 이미 호출, `Dashboard.jsx:329`)와 `deriveAttachmentStats`의 `gardenPoints`뿐이다. 추가 네트워크 호출 0.
- 이름 충돌 방지: 기존 화면의 "단계"는 크기 5단계(Tiny~Max)를 뜻한다 (`Dashboard.jsx:746`). 새 표시는 "승급 n단계"로 구분하고, 크기 단계 문구와 한 줄에 섞지 않는다. 장기적으로 크기 5단계 문구를 8단계가 대체할지는 Q1.
- **후퇴 방지**: `fetchXpTotal`은 오류 시 0을 돌려준다 (`wordLibrary.js:3681`). 그대로 쓰면 일시 오류에 단계가 1로 "후퇴"해 보인다. 제안: 오류와 실제 0을 구분하거나, 오류면 승급 표시를 숨긴다. (코드 수정은 이 문서 범위 밖이며 구현 단계의 항목이다.)

## 4. 기존 학생 기록 활용

- 승급 단계는 `f(xp, gardenPoints)`의 **순수 함수**다. 저장 필드가 없으므로 백필·마이그레이션이 필요 없다.
- 기존 학생은 첫 로드에서 자기 누적 XP와 학습 단어 수로 바로 단계에 안착한다. 이미 쌓인 XP 원장이 곧 입력이다.
- 안착 예(위 2.2 기준): XP 60 + 학습 단어 8 -> 3단계(주황). XP 300 + 학습 단어 25 -> XP 기준 6단계지만 단어 하한(6단계 40)에 걸려 5단계(파랑).
- 한계(정직하게): XP 원장은 2026-07 도입이라 그 이전 학습량은 반영되지 않고, 2026-07 이후에도 XP 전송 실패분은 영구 유실된다 (감사 P3, `REWARD_PATH_AUDIT_2026-09-11.md` 표 B 1-4행). 오래 다닌 학생이 예상보다 낮은 단계에 놓일 수 있다. 운영자 질문 Q4.
- 현재 분포 확인 방법(제안): 운영자가 Supabase에서 `xp_totals`의 학생별 total_xp 분포를 읽기 전용으로 집계해 2.2 경계로 몇 명이 어느 단계에 놓이는지 사전 확인한다. 에이전트는 DB를 조회하지 않았다.
- 학생 식별은 항상 `students.id`(UUID)다 (`usePaulRank(studentId)`). 이름 매칭 없음.

## 5. 수집 모자와 승급 모자의 공존

| 항목 | 제안 |
|---|---|
| 역할 | 승급 모자 = 진행 표시 + **기본 모자**. 수집 모자 = 학생이 고르는 **장착 모자** |
| 표시 우선순위 | 1) 유효한 장착 수집 모자 2) 승급 단계 모자 3) 폴백 (기존 👑 대신 1단계 핑크) |
| 같은 색 중복 | 장착 모자와 승급 모자가 같은 색이어도 한 번만 그린다. 라벨 "승급 n단계 · 수집 모자 장착 중" |
| 이중 지급 금지 | 승급은 `hatInventory`에 아무것도 쓰지 않는다. 수집 모자 해금 규칙(`HAT_THRESHOLDS`)은 무변경 (`hatSystem.js:30-37`) |
| 비교 | 승급은 후퇴하지 않는 진행(XP 단조), 수집은 append-only라 서로 상충하지 않는다 |
| 이름 | 승급 모자는 "승급 모자 n단계 (색)", 수집 모자 이름(`hatSystem.js`의 색 이름 포함)과 구분 |
| 축하 | 수집 모자는 기존 획득 의식 (`useAttachment.js:117` -> HatCeremony). 승급은 의식 없이 진행 막대만 먼저. 의식을 원하면 "마지막으로 본 단계"를 `studentId` 키 로컬 저장 (`localStorage`, DB 아님) |
| 중복 색 정리 | 수집 8색과 승급 8색은 순서만 다를 뿐 같은 8색 집합이다 (pink/red/orange/green/blue/navy/purple/gold). 즉 한 학생이 승급 3단계(주황)이고 수집 주황을 아직 못 얻을 수 있다. 이것은 의도된 비동기다 |

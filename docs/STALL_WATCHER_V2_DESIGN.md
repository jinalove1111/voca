# Stall Watcher V2 — 원인 분석 및 개선 설계 (2026-08-17)

**상태: 설계 문서만. watcher 코드는 이번에 수정하지 않는다(운영자 지시).**

V1 구현체: `scripts/hooks/claudeHeartbeat.mjs`(기록) + `scripts/watchClaudeStall.ps1`
(판정/알림) + `.claude/settings.json` 훅 6종. 작업 완료 알림(Stop 훅 →
`notify-windows.ps1`)은 정상 작동 중이며 V2에서도 **그대로 유지**한다.

## 2. 근본 원인 (3개가 동시에 작용)

### 원인 A — watcher가 수동 실행이라 아예 떠 있지 않았다

`watchClaudeStall.ps1`은 `npm run watch:claude-stall`로 운영자가 직접
띄워야 하는 상주 프로세스다(재부팅 자동 실행은 V1 범위에서 의도적으로 제외).
두 사고 당시 이 프로세스는 실행 중이 아니었다. **알림을 낼 주체가 없었다.**

### 원인 B — `tool-running` 상태가 무한정 정상으로 간주된다 (핵심)

heartbeat의 상태 모델:

```
pre(PreToolUse)  → tool-running   ← 알림 금지(정상 실행 중으로 간주)
post/prompt      → active         ← 유일한 stall 후보
stop/notification→ waiting-user   ← 알림 금지
session-end      → session-ended  ← 알림 금지
```

서브에이전트가 도는 동안 부모 세션은 `Agent` 툴 호출 **안에** 머무른다.
즉 PreToolUse가 남긴 `tool-running`이 22시간 내내 유지되고, watcher는 이를
"npm build가 정상 실행 중"과 **구별할 수 없다**. 오탐 방지를 위해 넣은 규칙이
정확히 이 케이스에서 미탐(false negative)을 만들었다.

실측 근거: 사고 당시 heartbeat 파일 내용이
`{"state":"tool-running","event":"pre",...}` 였다.

### 원인 C — heartbeat는 "살아있음"만 증명하고 "진전"은 증명하지 않는다

heartbeat는 훅이 불릴 때마다 타임스탬프를 갱신한다. 에이전트가 같은 파일을
반복해서 읽거나 같은 명령을 재시도하는 루프에 빠지면 heartbeat는 계속
찍히지만 **실질적 진전은 0**이다. V1에는 진전을 판단할 지표가 없다.

## 3. V2 설계

### 3.1 상시 실행 (원인 A 해결)

수동 실행을 폐기하고 **Windows 작업 스케줄러 등록**으로 전환한다.

- 트리거: 사용자 로그온 시 + 1분 주기 반복
- 동작: watcher가 이미 실행 중이면 즉시 종료(단일 인스턴스 뮤텍스), 아니면 기동
- 상주 프로세스가 아니라 **1분마다 1회 판정 후 종료**하는 방식(`-Once`)도 가능 —
  CPU 점유 0, 죽어도 다음 1분에 자동 복구되므로 이쪽을 권장
- 등록/해제 스크립트를 별도 제공하고, 등록 여부는 운영자가 결정

### 3.2 3단 상태 모델 (원인 B 해결)

`tool-running`을 무조건 면제하지 않고, **툴 종류별 기대 소요시간 상한**을 둔다.

| 상태 | 임계 | 알림 문구 |
|---|---|---|
| `active` (Claude 생성 중) | 5분 | Claude 작업 확인 필요 |
| `tool-running` (일반 명령) | 20분 | 명령이 오래 걸립니다 — 확인 필요 |
| `subagent-running` (신규) | 30분 **또는 진전 정지 15분** | 서브에이전트 진행 없음 — 확인 필요 |
| `waiting-user` / `session-ended` | 면제 | — |

`subagent-running`은 PreToolUse 훅이 **툴 이름을 보고** 구분한다(`Agent`/`Task`
계열이면 별도 상태로 기록). 훅에 전달되는 툴 이름을 heartbeat에 함께 남기면
되므로 추가 인프라가 필요 없다.

### 3.3 진전 지표 (원인 C 해결)

heartbeat 갱신만으로는 부족하므로, watcher가 **독립적으로 관측 가능한 진전
신호**를 함께 본다. heartbeat가 계속 찍혀도 아래가 전부 정지면 stall로 판정:

1. **작업 디렉터리 최신 파일 mtime** — 저장소 내 파일(`.git` 및 `dist/` 제외)
   중 가장 최근 수정 시각. 코드를 쓰고 있으면 반드시 갱신된다.
2. **툴 호출 카운터** — heartbeat에 단조 증가 시퀀스 번호를 넣어, 번호가
   멈췄는지 본다(같은 상태로 재기록만 반복되는 경우 감지).
3. 두 지표가 모두 임계(15분) 이상 정지 + 프로세스 생존 → **stall 확정**.

이 조합이면 "오래 걸리는 정상 빌드"(파일 mtime은 멈춰도 툴 카운터가 곧
증가)와 "진짜 정지"(둘 다 정지)를 구분할 수 있다.

### 3.4 중복 방지 / 복구 (V1 동작 유지)

- 알림 시 `lastAlertedKey`(heartbeat ts + 진전 지표 스냅샷)를 상태 파일에 기록,
  같은 stall에서는 재알림 금지 — V1에서 이미 검증된 방식 그대로.
- 진전이 재개되면(mtime 또는 카운터 변화) stall 상태 자동 해제.
- 해제 후 다시 임계를 넘으면 키가 달라지므로 **새 알림 허용**.
- 반복 stall에 대해서는 2회차부터 알림 간격을 늘리는 백오프(5분 → 15분 → 30분)를
  두어 알림 피로를 막는다.

### 3.5 작업 완료 알림 (변경 없음)

Stop 훅 → `notify-windows.ps1` "Task finished" 경로는 그대로 둔다. V2 변경은
전부 stall 감지 측에만 적용한다.

## 4. 검증 계획 (구현 시)

V1과 동일하게 시간 단축 시뮬레이션으로 검증한다(`-StallSeconds` 축소 + 상태
파일 주입). 필수 케이스:

1. 정상 빌드 20분 미만 → 알림 없음
2. `subagent-running` + 진전 지표 정지 15분 → 알림 1회
3. `subagent-running` + 파일 mtime 계속 갱신 → 알림 없음(정상 진행)
4. heartbeat만 갱신되고 진전 지표 전부 정지 → 알림(원인 C 회귀 고정)
5. 같은 stall 재확인 → 중복 없음
6. 진전 재개 → 리셋 / 재정지 → 새 알림
7. Claude 프로세스 사망 → 알림 없음
8. 작업 완료 알림 정상(회귀 없음)

특히 **2번과 4번은 이번 두 사고를 그대로 재현한 회귀 테스트**이므로 반드시
포함한다(수정 전 코드로 FAIL 실측 후 구현 — 저장소 규칙 15).
